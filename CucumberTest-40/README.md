# ParaBank Cucumber — Assignment 3 (Group 40)

This Maven project implements Behaviour-Driven Development (BDD) acceptance tests for the ParaBank demonstration banking website using **Cucumber, Gherkin, Selenium WebDriver, Java and JUnit Platform**. The suite covers **Transfer Funds, Bill Pay and Request Loan**, including successful and unsuccessful behaviours.

This is the **reviewed 37-scenario version**. The project ZIP supplied with this README includes the Maven `pom.xml`, Cucumber feature files, Java step definitions and test runner. No patching or file replacement is required after extracting the complete ZIP.

## Open and run

1. Extract the complete project ZIP to a **new folder**. Keep earlier versions as backups.
2. In IntelliJ IDEA, choose **File > Open** and select the extracted project folder containing `pom.xml`.
3. Import/load the Maven project and allow dependencies to download.
4. Use **JDK 17 or later** and have **Google Chrome** installed.
5. Run `src/test/java/com/parabank/runner/RunCucumberTest.java` as a JUnit test, or open a terminal at the project root and run:

   ```powershell
   mvn clean test
   ```

6. To execute only one functionality, use one of the following commands:

   ```powershell
   mvn test '-Dcucumber.filter.tags=@transfer'
   mvn test '-Dcucumber.filter.tags=@billpay'
   mvn test '-Dcucumber.filter.tags=@loan'
   ```

7. Review `target/cucumber-report.html`, `target/cucumber.json`, `target/cucumber.xml`, `target/rerun.txt` and `target/surefire-reports/`, as generated by the runner.

**Important:** A complete run may finish with Maven `BUILD FAILURE` because some acceptance tests deliberately expose behaviour that does not satisfy their expected outcomes. That is different from a Java compilation or test-discovery failure. Do not weaken assertions or suppress failing scenarios to force a successful build.

## Test data and account setup

- Each scenario creates and logs in to a **fresh ParaBank demo customer** rather than requiring preconfigured credentials.
- The test setup establishes **two accounts** and checks their opening balances before executing banking operations.
- Account IDs are selected dynamically rather than hard-coded.
- Transaction assertions verify confirmations, account balances and, for successful loan applications, the creation of a loan account where applicable.
- No `PARABANK_USERNAME` or `PARABANK_PASSWORD` environment variables are required by this version.
- ParaBank is a shared public demo service: server errors, resets and temporary availability problems can influence execution.

### Observed application behaviour behind the failures

- **Transfer Funds (3 failures):** Zero and negative transfer amounts were accepted; a non-numeric transfer amount triggered a generic internal server error instead of useful validation.
- **Bill Pay (2 failures):** Zero and negative payment amounts were accepted, including a negative payment that increased the source-account balance.
- **Request Loan (5 failures):** Invalid or missing inputs triggered a generic internal server error instead of appropriate field-level validation.

These are **observed deviations from the test expectations**; they should not be represented as passing acceptance tests. The earlier scenario that treated a generic internal error as a successful Request Loan rejection was corrected. During this 37-scenario run, there were **no failures due to an unavailable Accounts Overview page**.

Some expected rejection rules represent test acceptance assumptions unless explicitly specified by ParaBank. Conclusions about contractual banking rules should not be inferred solely from this demonstration application's behaviour.

**Reporting note:** The counts above are from the final 37-scenario run, not from the earlier 47-scenario version. Generated reports must come from the same run and version of the source. If you rerun `mvn clean test`, the `target` directory is regenerated; save any required evidence before rerunning.

## Known limitations

ParaBank is a public demonstration application and may intermittently return internal server errors or reset application data. Some invalid-input tests therefore fail against its current implementation. These failures are retained so that the automated tests report the actual results honestly. The suite tests expected acceptance behaviour; it does not assert that ParaBank enforces real-world lending or overdraft policies unless such policies are independently specified.
